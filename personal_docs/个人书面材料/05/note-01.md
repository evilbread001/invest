## 我的系统架构（面试必背）

```
建树层（Hermes + Skill）         诊断层（自建纯Workflow）
────────────────────             ────────────────────────
输入：8D/FMEA/会议记录            输入：新工单
  ↓ Skill检索（历史经验）          ↓ 加载OWL故障树
  ↓ LLM提取诊断逻辑               ↓ 规则驱动动态路由
  ↓ JSON中间结果存储               ↓ 等人工输入测量值
  ↓ SQLite图结构校验               ↓ 阈值规则判断下一步
  ↓ 生成OWL文件                   ↓ 诊断结论 + 8D报告
  ↓ 提炼新Skill入库
           ↕ Hook拦截所有工具调用
┌─────────────────────────────────────────────────┐
│  industrial-control（预防层）                     │
│  工具风险评估 / Playbook约束 / 资源锁 / 速率限制   │
│               ↓ 记录阻止事件                      │
├─────────────────────────────────────────────────┤
│  industrial-evidence（审计层）                    │
│  SHA-256哈希链 / 证据块验证 / 任务生命周期追踪     │
└─────────────────────────────────────────────────┘
```

**关键设计决策：**
- 诊断运行时用规则路由而不是LLM路由：路由条件是精确的阈值判断，规则完全能表达，同时保证可复现和可审计
- 建树用Hermes：Skill系统积累领域经验，同类产品越做越快越准
- 两个插件：预防+审计双层保障，满足汽车电子质量合规要求

## 模块一：Agent核心概念

### Agent vs Chatbot vs Workflow

| | Chatbot | Workflow | Agent |
|--|---------|----------|-------|
| 决策者 | 模型 | 代码逻辑 | 模型 |
| 流程 | 固定 | 固定 | 动态 |
| 工具 | 无 | 有但写死顺序 | 模型自决定 |

**Agent = 能感知环境、自主决策、调用工具、根据结果调整行为的LLM应用**

### 四个核心组件

| 组件 | 作用 | 我们系统里的体现 |
|------|------|----------------|
| Planning | 把目标拆解成多步 | 建树时LLM决定提取哪些信息 |
| Memory | 短期/长期记忆 | Skill库（长期）+ Context（短期）|
| Tool Use | 调用外部能力 | 文档解析、OWL写入等tools |
| Action | 执行落地 | 写入OWL文件、触发诊断流程 |

### ReAct设计模式

**核心循环：** Thought → Action → Observation → Thought → ...

**为什么主流框架都用它（面试三要点）：**
1. 推理过程可见，Thought显式化，可调试
2. 错误可自我修正，Observation把错误反馈给模型
3. 实现简单，一个prompt + while循环

**ReAct的问题（同样要会说）：**
- Token消耗大、可能不收敛、行为不可控、延迟高
- 实践中都是"ReAct + 约束"，纯ReAct只在研究里用

## 模块二：上下文管理

### 四种策略

| 策略 | 原理 | 适合场景 |
|------|------|---------|
| 滑动窗口 | 只保留最近N轮 | 简单对话，对历史依赖不强 |
| 摘要压缩 | 定期压缩历史为摘要 | 长对话，需保持连贯 |
| 选择性保留 | 按重要性打分，优先保留高价值内容 | 复杂多步骤任务 |
| 外部记忆 | 存到向量库，需要时检索回来 | 需要长期记忆的场景（RAG） |

### Claude Code的实现
- 历史接近上限时自动压缩摘要
- 跨会话信息存MEMORY.md等外部文件
- 按需读取相关文件，不全量加载

### Hermes的实现
- Skill系统：任务完成后提炼成几百token的Skill文档
- 下次只加载相关Skill，不加载完整历史
- **本质：把摘要压缩+选择性保留做到了框架层面**

### Hermes的上下文管理局限（实际踩坑）
Hermes设计重心在跨任务长期记忆（Skill积累），单次任务内没有自动压缩机制。处理长篇FMEA或多份8D报告时容易超限。

**我们的解法：**
- 文档分块处理，每次聚焦一个子系统
- 中间结果存JSON文件，不留在对话历史里
- 后续步骤基于结构化JSON而不是原始文本

### 建树pipeline中间结果存储

```
原始文档 → 分段文本（不存，重算成本低）
         → 故障/根因/措施列表（JSON文件，按客户/产品分目录）
         → 因果关系对（追加进同一JSON）
         → 节点+关系（SQLite，用于图结构校验）
         → OWL文件（文件系统）
```

**SQLite校验内容：** 根节点唯一性、循环依赖检测、孤儿节点检查

**JSON存储的额外价值：** 历史提取结果可作为Hermes Skill的参考材料，下次同类产品直接注入典型因果关系对

## 模块三：Tool Calling与异常处理

### 完整流程

```
用户输入 → LLM返回tool_call（工具名+参数）
         → 你的代码执行工具
         → 结果作为tool_result返回LLM
         → LLM继续推理或给出最终答案
```

**关键：LLM不执行工具，只是"提议"，执行是你的代码。**

### Parallel Tool Calling
LLM一次返回多个tool_use，代码并行执行，等全部结果再统一返回。
适合多个独立工具调用，有顺序依赖时关闭或手动控制顺序。

### 三种异常处理策略

**1. 把错误反馈给模型（最重要）**
```python
tool_result_content = f"工具执行失败：{str(e)}。请检查参数或尝试其他方法。"
# 不管成功失败，都把结果还给模型，让它自我修正
```

**2. 重试机制（临时性错误）**
- 超时/503 → 指数退避重试
- 参数错误/权限不足 → 不重试，直接反馈给模型

**3. Fallback降级**
实时接口挂了 → 降级到缓存 → 最终兜底返回空数据+提示

**防止无限循环：** 设MAX_ITERATIONS，超出强制结束

### 我们项目里的tool calling（建树pipeline）

Tool calling在建树pipeline中用强制schema约束OWL输出。
异常处理：
- 格式不符合OWL schema → 把校验错误反馈给模型，最多重试3次
- 业务规则违反（循环依赖、根节点不唯一）→ 代码层验证，错误描述反馈给模型
- 诊断运行时是确定性规则引擎，不涉及tool calling

## 模块四：指令遵循稳定性

### 不稳定的根本原因
LLM是概率模型，在预测"下一个最可能的token"，不是在执行指令。

### 六个提升手段

| 手段 | 做法 |
|------|------|
| System Prompt分层 | 角色/任务/格式规范/边界处理各司其职 |
| Structured Output | 用tool的强制schema约束输出，比prompt更可靠 |
| Few-shot示例 | 让模型"看"正确格式，比"读"规则更有效 |
| 任务拆解 | 一次只做一件事，先提节点→再建关系→再生成OWL |
| 温度控制 | 格式化输出场景temperature设0 |
| 正向指令 | "只输出JSON，第一个字符是{" 优于 "不要输出多余内容" |

### 代码层验证+重试
所有LLM输出过schema验证和业务规则验证，失败时把具体错误信息反馈给模型重试。

## 模块五：框架对比

### 纯Workflow vs LangGraph vs 纯ReAct

```
确定性 ←————————————————————→ 自主性
纯Workflow    LangGraph    纯ReAct Agent
（我们诊断层） （中间地带）   （Hermes建树）
完全确定性规则  图结构+条件路由  模型自主决策每步
```

### 我们的诊断Workflow vs LangGraph

**相同点：** 都是动态路由，根据中间结果决定下一步

**核心区别：**

| | 我们的Workflow | LangGraph（如果用LLM路由） |
|--|--------------|--------------------------|
| 路由决策者 | 确定性规则（if 电压<3.5V） | LLM判断 |
| 可复现性 | 100% | 有不确定性 |

**为什么不用LangGraph：**
- 路由条件是精确阈值判断，规则完全能表达，不需要LLM的语义理解
- 规则驱动保证相同输入100%复现，满足汽车电子可审计要求
- 故障树本身已经是最好的路由决策器，LLM路由是多此一举

### LangGraph额外提供的能力
- Checkpoint（中断恢复）
- Human-in-the-loop内置支持
- TypedDict状态类型安全
- 图结构可视化debug

### Hermes Agent深度

**核心设计：越用越聪明**
- 任务完成后把经验提炼成Skill文档（结构化，几百token）
- 下次检索相关Skill注入context，不带完整历史

**三层记忆：**
```
Working Memory（当前任务对话历史，任务结束清空）
      ↓ 提炼
Skill Library（结构化经验，持久化，语义检索）
      ↓ 长期积累
Persistent Memory（用户偏好、工作环境，每次启动加载）
```

**MCP协议支持：** 原生支持，工具集成成本低

**实际局限：** 单次任务内没有自动上下文压缩，处理长文档容易超限，需要在应用层做窗口控制

## industrial-control插件

**定位：** 工业AI安全管制层，通过Hook机制不侵入Agent主逻辑

**8个Hook注册顺序：**
```
pre_tool_call[0]  → 速率限制检查
pre_tool_call[1]  → 全局策略评估 + 审计
pre_tool_call[2]  → Playbook白名单检查
pre_tool_call[3]  → 阻止危险git命令
pre_llm_call[0]   → 注入Playbook提示词 + 行动计划
post_llm_call[0]  → 解析<action_plan>块
on_session_start  → 预热Playbook缓存
on_session_end    → 释放所有锁
```

**4个核心工具：** action_plan / playbook / resource_lock / task

**Playbook系统：**
- 不同任务类型对应不同工具白名单/黑名单
- 告警诊断：只读，不能写入设备
- 参数建议：只能输出建议，不能直接执行变更
- 支持运行时切换Playbook（P11特性）

**风险分类：**
- Critical：PLC写入、设备控制命令 → 直接阻断
- High：开放web访问、委托任务
- Medium：技能变更、可写工具
- Low：只读操作

## industrial-evidence插件

**定位：** 审计追踪与证据链校验，配合industrial-control使用

**5个Hook：**
```
on_session_start      → 初始化SQLite schema
post_tool_call        → 记录已允许的工具调用
post_llm_call         → 记录LLM回复事件
transform_llm_output  → 验证证据块格式
on_session_end        → 验证哈希链完整性
```

**SHA-256哈希链：**
```
row_hash = SHA256(prev_hash + "\n" + canonical_json(payload))
```
任何对历史记录的篡改都会破坏后续哈希链，verify命令可随时校验。

**证据块要求（最终回复必须包含）：**
```json
{
  "conclusion": "...",
  "evidence": [...],
  "cited_sources": [...],
  "risk_level": "low|medium|high|critical",
  "recommended_action": "...",
  "approval_required": true|false
}
```

**两插件协作：**
- control阻止工具调用 → 调evidence API记录"被阻止"事件
- evidence的hook记录"被允许执行"的事件
- 合起来 = 完整审计链（不管允许还是阻止，全都有据可查）

## 面试高频Q&A

### Q1：上下文管理的实践（结合项目）
> 在建树pipeline里遇到过上下文超限。解法是分块处理长文档，中间结果存JSON文件不留在对话历史，后续步骤基于结构化JSON而不是原始文本。Hermes的Skill系统解决了跨任务记忆，但单次任务内需要在应用层自己做窗口控制。

### Q2：为什么主流框架都用ReAct？
> 推理过程可见可调试、错误可自我修正（Observation机制）、实现简单灵活。但纯ReAct生产环境不稳定，实践中都是"ReAct+约束"：LangGraph加状态图，Hermes用Skill约束行为模式，我们诊断运行时直接用确定性规则引擎替代。

### Q3：指令遵循稳定性怎么做？
> 三层：prompt分层设计+few-shot示例+正向指令；tool schema强制约束输出格式；代码层schema验证+业务规则验证，失败时把具体错误反馈给模型重试，任务拆成多步每步只做一件事。

### Q4：Tool calling异常怎么处理？
> 建树pipeline用tool schema强制约束OWL输出。异常分两类：格式异常把校验错误反馈给模型重试（最多3次）；业务规则违反（循环依赖等）在代码层图结构验证后反馈给模型。诊断运行时是确定性引擎，不涉及tool calling，异常用传统工程手段处理。

### Q5：为什么不用LangGraph做诊断运行时？
> 我们的路由条件是精确阈值判断，规则完全能表达，不需要LLM语义理解。规则驱动保证100%可复现，满足汽车电子可审计要求。LangGraph适合路由逻辑本身需要语义判断的场景，我们故障树已经是最好的路由决策器，引入LLM路由反而降低可靠性。

### Q6：工业场景安全合规怎么保障？
> 两个插件：industrial-control（预防层）通过Playbook约束LLM在特定任务的工具边界，阻断PLC写入等高危操作，资源锁防止多任务并发冲突；industrial-evidence（审计层）用SHA-256哈希链记录所有工具调用和LLM回复，防篡改，强制最终回复包含结构化证据块。两者协作形成完整审计链，满足汽车电子质量流程的可追溯要求。

### Q7：系统设计题——设计工业诊断Agent
> 分两层。知识构建层用LLM处理非结构化文档自动建故障树，Hermes Skill积累领域经验。诊断运行层用确定性规则引擎执行故障树，规则驱动动态路由，不引入LLM路由。工程重点：建树质量评估和Skill人工review机制、多客户环境隔离、诊断路径完整审计日志。

## 模块六：RAG基础

### 为什么Agent需要RAG
- 解决两类问题：模型知识截止、Context Window有限
- 核心思路：用时检索，按需注入，而不是把所有知识塞进模型
- 项目里的两个典型场景：
  1. 建树时检索历史8D/FMEA案例，作为few-shot参考
  2. 客服问答里检索知识卡片、历史工单和用户画像相关信息

### 完整RAG Pipeline
```
离线阶段：原始文档 → 文本切块 → Embedding → 向量库索引
在线阶段：用户查询 → 查询向量 → Top-K检索 → 注入Prompt → LLM生成答案
```

### 关键环节

#### 1. 文本切块（Chunking）
- 固定长度切块简单但效果一般
- 语义边界切块更适合工业/客服场景
- 对你们场景的建议：
  - 8D报告按D步骤切块
  - FMEA按功能模块切块
  - 客服知识库按知识卡片天然切块
- 经验值：300-800 token，带50-100 token overlap

#### 2. Embedding模型
- 查询和建索引必须用同一个embedding模型
- 中文工业场景要选支持中文语义的模型

#### 3. 向量数据库
- 轻量：Chroma
- 生产级：Milvus / Qdrant
- 已有PostgreSQL时最低成本方案：pgvector
- 适合你们，因为主系统已经用PG，可以少引入一套新基础设施

#### 4. 检索策略
- 基础：向量相似度检索（语义检索）
- 进阶：混合检索（向量 + 关键词）
- 对工业/客服场景特别重要，因为型号、SN、零件号、工单号等精确词汇很多，纯语义检索容易漏

#### 5. Reranker精排
- 初步检索多一些候选，再用CrossEncoder精排
- 适合L3复杂推理或需要更高质量召回的场景

### 检索质量优化
- **元数据过滤**：先按客户/产品/product_scope缩小范围再检索
- **small-to-big retrieval**：索引时切小块，返回时扩展为父块
- **混合检索**：BM25 + 向量 + RRF融合
- **结果去重**：同一knowledge_id多次命中时只返回引用摘要，不重复全文

### 你们客服Agent里的RAG设计（从方案文档提炼）

#### 三种检索模式
| 模式 | 策略 | 适用 |
|------|------|------|
| fast | BM25 + 向量（RRF融合） | L2常规检索 |
| balanced | BM25 + 向量 + Reranker | L3 / L2精确检索 |
| thorough | BM25 + 向量 + Reranker + 放宽filter重试 | L3兜底 |

#### 用户问题改写（两层）
- **LLM语义级改写**：综合多轮信息、去噪、结构化，生成search_query
- **Handler规则级优化（可选）**：同义词归一、关键词提取、already_tried排除
- 初版先依赖LLM改写，必要时补Handler规则层

#### 检索结果呈现策略
- 1条高置信命中 → 直接交付方案
- 2-3条候选且有明确区分条件 → 追问区分条件
- 3-5条候选但区分条件不明确 → 展示候选列表（用通俗描述）
- 0条命中 → 追问更多信息 / 转人工

#### 多轮检索的上下文管理
- Handler层：同一knowledge_id第二次返回时只给引用摘要
- 对话>5轮：压缩旧tool result为摘要
- 新结果带supersedes_previous标记，确保LLM以最新结果为准

### 项目面试话术

**Q：RAG是什么，解决什么问题？**
> RAG是检索增强生成，解决两个问题：一是LLM知识截止，新产生的数据模型不知道；二是上下文有限，历史数据全量塞不进去。做法是把知识库向量化存到向量数据库，用户查询时先检索最相关的片段，注入context给LLM回答。核心优势是知识可以实时更新，不需要重新训练模型。

**Q：RAG检索质量不好怎么优化？**
> 几个层面：切块策略上按语义边界切而不是固定长度，保证单块信息完整；检索策略上用混合检索（向量+关键词）避免精确词汇被漏掉，对我们工业和客服场景尤其重要，因为有大量型号、零件号、SN这类关键词；检索后加Reranker精排，过滤低质量结果；查询时加元数据过滤，比如先按客户/产品或product_scope缩小范围再做向量搜索。

**Q：你们项目里RAG怎么用？**
> 在建树pipeline里用RAG检索历史成功案例：新文档进来时，先检索同类产品的历史故障树结构作为few-shot注入prompt，LLM参考历史案例生成新的OWL。客服Agent里则把知识卡片向量化，支持BM25+向量的混合检索，并根据问题复杂度切换fast/balanced/thorough三种检索模式。Hermes的Skill系统和RAG是互补的——Skill存提炼后的通用经验，RAG存具体历史案例和知识卡片细节。

## 客服Agent项目（Hermes agentic 架构）

### 架构定位
- 这是一个更纯粹基于Hermes Agent的项目，与工业诊断Agent不同
- 工业诊断项目：建树是agentic，运行时是确定性workflow
- 客服Agent项目：问答流程本身就是agentic + RAG + 双模式（自主 / Copilot）

### 总体流程亮点
1. **多模态预处理**：图片/GIF/视频先用Qwen3-VL-8B转成文字描述，再进入主流程
2. **L1关键词层**：转人工、问候、辱骂等确定性信号直接拦截，不调LLM
3. **追问续接检测**：如果session_state.pending_question存在，则跳过意图识别，直接续接主模型推理
4. **双模型策略**：Qwen3.5-9B做意图识别+路由，Qwen3.6-27B做主推理
5. **L2/L3策略**：
   - L2：知识检索 + 简单结构化查询（覆盖95%+）
   - L3：多源推理 + ontology关系遍历（复杂case）
6. **Autonomous / Copilot双模式**：自动回复用户，或转人工后给坐席结构化建议
7. **Session结束后的异步分析**：对话总结、用户画像更新、诊断分析

### 我负责的部分

#### 1. 用户画像Skill
流程：
```
session结束
  ↓ 从对话历史提取增量信息（LLM抽取）
  ↓ 结构化输出：产品信息 / 问题标签 / 技术水平 / 情绪记录
  ↓ 通过ontology MCP写入Customer实体
  ↓ 下次进线时加载，缩窄检索范围 / 适配沟通风格 / 识别重复进线
```

面试重点：
- 这是知识图谱的增量更新，不是静态导入
- LLM从非结构化对话中提取结构化用户信息
- 用户画像反哺推理：known_products缩窄product_scope，tech_level影响回复风格

#### 2. 评测闭环模块
- L0：离线检索评测（验证RAG hit rate，不调LLM）
- L1：单轮对话评测（工具选择+回复质量）
- L3：端到端评测（UserSimulator驱动100个case，LLM Judge打分）
- Bad case分析页面：可视化看失败case、上下文快照、推理过程

面试重点：
- 很多团队没有系统化评测闭环，你们有
- 用UserSimulator做端到端自动回归测试
- LLM Judge评估解决率和回复质量，知识库或Skill改动后可量化对比

### 这个项目的面试叙事
> 我目前参与两个Agent项目。一个是工业质量诊断Agent，我是负责人，已在多家车企生产环境上线，是混合架构——建树用Hermes做LLM提取，诊断运行时用确定性规则引擎。另一个是智能客服Agent，基于Hermes做更纯粹的agentic架构，我负责用户画像Skill和评测闭环模块，现在已经有demo代码仓库。两个项目分别体现了不同场景下的架构选择：一个强调可控和可审计，一个强调自主推理和知识复用。

### 客服Agent的技术亮点（面试可讲）
- 双模型分工：小模型做路由，大模型做推理，成本与质量平衡
- L1/L2/L3分层：能不用LLM就不用，减少延迟和成本
- 混合RAG：BM25 + 向量 + RRF + Reranker
- 多模态接入：VL模型处理图片/GIF/视频
- Autonomous/Copilot双模式：同一个Agent支持自主回答和坐席辅助
- Session后异步分析：conversation_summary / user_profile_analysis / diagnostic_analysis
