# 产线诊断 Agent：当前确认版（2026-10-19）

用户已确认这版产品和技术方案可以作为阶段性整理基线。本文用于后续项目经历整理、演示与模拟面试；记录现有实现，不等同于生产发布，也不表示所有后续优化已经完成。

## 1. 产品定位与价值

面向制程故障定位，保留专家故障树作为可复用的辅助排查路径，同时允许工程师提出假设、补充现场证据并依据已验证结论结束诊断。核心原则：故障树辅助工程师，而不是工程师解决问题后仍必须完成的打卡表。

Agent 的价值不在于替代专家做所有判断，而在于减少查询、整理、记录与协作成本：不知道如何排查时提供标准路径；有判断方向时组织验证和证据；发现树外原因时保留结论并形成知识补全建议。没有把这些价值推算为未经测量的效率或准确率指标。

## 2. 当前交互与产品闭环

### 2.1 三栏界面

- 左栏：本地工单列表、状态筛选和搜索。
- 中栏：工单状态、假设与证据、专家结论、任务卡片、辅助路径、报告与操作记录。树外结单后，顶部展示故障树补全建议。
- 右栏：自然语言对话，解释检查、登记线索、整理证据、提出待确认操作。
- 对话和卡片使用同一后端工单状态。页面依据结构化响应更新，不从模型回复中的“已完成”推导执行结果。

### 2.2 三种诊断方式

1. **按树排查：** 原引擎激活检查项，工程师提交合法选项，恢复执行并生成后续卡片。
2. **围绕假设协作：** 工程师提出怀疑，Agent 记录假设、调用可用分析工具、记录人工验证，展示支持与反对证据及缺口。统计关联和观察异常不直接等于因果确认。
3. **专家结束：** 工程师认为根因已验证，模型起草结论；人工核对证据、反对记录和未查项，署名确认后结束外层工单。原树未完成项保持未查或暂缓，不伪装为已完成。

新异常可先登记为线索，并检索原树 TEST 目录。符合当前逻辑前置条件的同层检查可提出补查；暂缓原项和创建补查可以合并为一次待确认提议。补查结果独立保存，原树正式激活同一条件后，人工再次核对适用性才能复用。不能按同名检查跨分支误用证据。

## 3. DSH 与 BPMN/OWL 的接入方式

不是将 BPMN 改写为 DSH 工作流，也不是让大模型接管故障树路由。当前分工如下：

| 层次 | 实现及职责 |
|---|---|
| DSH | 复用 AgentLoop、ToolRuntime、SessionStore 与 Cordis；理解对话、选择工具、解释结果 |
| 诊断插件 | 暴露状态查询、检查说明、线索/假设/验证记录、分析、操作提议及专家结论草稿等领域工具 |
| DiagnosisStore | 统一管理工单、任务、证据、提议、版本和引擎快照；执行校验与持久化 |
| EngineBridge | Node 启动 Python 子进程，通过标准输入/输出交换 JSON；设置超时与大小限制 |
| Python 适配层 | 加载原执行代码与原 PCBA 树，隔离生产基础设施，交接快照及反馈 |
| 原 BPMN/OWL | BPMN 管理宏观阶段；项目原 OWL 故障树执行器计算诊断条件与后续路径 |

DSH 的业务工具和页面操作共同调用状态管理层。模型没有直接执行任意引擎命令的工具；需要推进原树的人工确认操作才进入 EngineBridge。

每次调用 Python 传入工单 ID、上次快照、已确认反馈及版本增量；原引擎恢复到等待点后继续执行，返回新快照、当前阶段、检查项、合法选项、路径和根因。不是保持一个 Python 进程长期等待工程师输入。这里的 OWL 指项目既有故障树框架，不宣称另接入通用 OWL/DL 推理器。

## 4. 一句话如何变成工作流反馈

示例：当前检查“检测 PCB 焊盘异物”，工程师说“已经检查，没有异物”。

1. 后端加载工单，将当前任务、合法答案、状态版本、已有证据及最近对话注入模型上下文。
2. 模型调用 `propose_action`，使用当前任务 ID、`kind=result`、`answer=否` 及工程师原话形成提议。
3. 后端验证后保存待确认提议；此时原任务没有完成，引擎没有推进。
4. 工程师点击确认，后端核对工单开放状态、revision、提议有效性、任务状态、答案选项及幂等键。
5. 将页面任务 ID 映射为原引擎 `execution_id`，携带快照及反馈调用 Python。
6. 原引擎决定下一步；后端保存新状态，将执行队列转换为任务卡片。

直接在任务卡提交答案会跳过自然语言解析与提议阶段，进入相同的状态校验和引擎执行入口。普通记录工具可以直接保存用户提供的线索、假设及验证，不要求所有工具调用都人工点击；这些记录不构成原树检查反馈。

| 输入/操作 | 协作状态 | 原引擎快照 |
|---|---|---|
| 询问检查方法 | 增加对话/调用轨迹 | 不推进 |
| 提出假设、补充验证记录 | 新增有来源的假设或证据 | 不推进 |
| 暂缓检查 | 人工确认后卡片变为暂缓 | 不提交答案 |
| 无法判断 | 标记待复核、保留缺口 | 不提交答案 |
| 创建及填报补查 | 保存独立补查任务及证据 | 不立即反馈原树 |
| 确认原任务有效结果/复用证据 | 保存人工反馈 | 恢复执行并更新 |
| 确认专家结论 | 结束外层工单，冻结诊断写入 | 保留历史，可能仍为 Waiting |

对话事件、协作工单状态、引擎快照是三种不同状态。模型文本不是状态真值。DSH 原始事件在内存，工单与展示对话写入本地 JSON；重启后重新注入领域状态及最近对话，不承诺完整 DSH 事件重放。单工单串行操作、版本校验和幂等控制用于防止确认过期提议及重复推进，不等同于分布式事务。

## 5. 故障树补全：结单后的独立流程

专家结单时选择“已覆盖 / 未覆盖 / 不确定”，仅“未覆盖”触发持久化生成任务。后台独立 DSH 会话只注册提交候选路径的工具，无审核或发布工具。

候选路径包含：原树挂接位置、与专家结论一致的根因、补全依据、1–6 个检查步骤、命中/其他结果、已有验证或建议补充标记，以及证据 ID。已有验证必须引用对应假设的人工报告；未知不能并入排除条件。此校验不替代专家对检查语义和证据充分性的判断。

页面生成完成后显示：

> 故障树补全建议  
> 本次结论未被当前版本覆盖，已生成候选路径。  
> 状态：待确认路径

用户可编辑候选内容，第一次署名确认形成锁定草稿；第二次独立确认发布。本地版本注册表保存于当前数据目录的 `knowledge/registry.json`，新工单加载已发布增量，旧工单维持原版本。新增路径通过原 OWL 类装配，低优先级追加；不删除或重排原分支，不修改生产仓库源码。

生成失败不撤销已完成结单，支持重试；打开工单可恢复待生成任务。发布前检查基础及父发布版本，并探测可装配性；冲突时拒绝覆盖。署名未经企业身份鉴权，两次确认不意味着必须由两个不同账号审批。当前无回滚界面或生产发布集成，编译探测也不是独立业务回放评测。

## 7. 面试讲述基线

> 我们把专家故障树作为确定性的辅助诊断能力，通过领域插件和进程桥接接入 DSH。自然语言用于理解现场描述、整理假设和证据、生成待确认操作；关键检查反馈由工程师确认后交给原 BPMN/OWL 恢复执行。工程师有树外已验证结论时，可以独立结束工单，系统保留未查项，再起草故障树补全路径，经人工确认草稿和再次确认发版后供新工单使用。
