## 客服项目的完整方案主线

项目要解决的不是单纯“把文档变成向量”，而是让客户既有知识能够支持客服 Agent 的具体业务决策。以知识卡为中间表示，将问题、适用机型、排查步骤、解决方案及媒体组织在一起，完成可追溯、可更新的入库链路，并与对话检索和派单流程衔接。

围绕查询表达与知识内容不匹配这一问题，方案从知识侧和查询侧两端处理：知识侧参考真实用户问法扩充相似问题；查询侧结合对话上下文组织检索问句，保留型号、症状及否定条件，不引入未经确认的根因。相似问入库前设置格式/重复检查、语义筛查及人工复核，控制错误扩充造成的误召回。

评测分两层：检索层固定卡片和模型配置，比较目标卡命中及误召回；端到端层用模拟用户验证客服流程，同时保留独立会话集检查对未参与调优数据的表现。整条主线用于组织后续实现和面试讨论，具体完成进度见文末，不意味着所有优化均已上线。

#### 4.2 真实 Bad Case 线索：Agent 查询与知识卡的表达不匹配

- [口述，2026-10-13] 本人参与 Bad Case 分析时，发现 Agent 提问/检索时生成的 query 关键词与知识库卡片内容的表达不一致；这是当前本人指出的主要问题。
- [代码背景] 客服端 `plugins/cs-agent/knowledge/processor.py` 使用意图结果中的 `kb_keywords` 拼出查询；检索客户端优先使用传入的 `user_message`。因此应同时检查原始用户话语、意图提取结果和最终发出的 query，不能只检查 embedding 或卡片正文。
- [边界] “用词不同”本身不足以证明检索失败的根因。需要区分：同义表达召回不足、query 提取时丢失关键条件、query 加入错误假设、产品范围过滤错误、正确卡已召回但排序靠后、Agent 未正确使用返回内容。以上是待排查方向，不是声称本人都遇到或修复过。

目标：不是“问句看起来与标题相似”，而是**该知识卡的答案能否在适用条件成立时回答该问句**。建议采用候选生成、规则预检、语义筛查、人工复核、回归验证五步，不必增加多 Agent 架构。

1. **有约束地生成候选。** 输入知识卡标题、产品范围、故障条件、答案和脱敏后的真实问法（只使用开发数据）。真实问法用于参考表达，不把其中缺乏卡片支持的症状/型号直接移植。初版每卡最多生成 3–5 条，允许不足；禁止增加未经支持的根因、更换产品、反转否定条件或将窄场景泛化。保留 card_id、来源、模型/prompt 版本和生成时间。
2. **规则预检。** 检查字符串/空值/长度，规范空白后精确去重，检查型号与单位等明显冲突。不要无差别删除型号中的符号；型号兼容需按现有产品映射，不只按字面是否相等。不设未经验证的 embedding 相似度阈值作为唯一准入标准。
3. **语义筛查。** 以一次独立的审核调用对照“原卡全文 + 候选问句”，输出 `accept/reject/review`、理由及卡片证据，检查适用产品、症状/否定条件、诉求、答案是否充分。无法判断走 review，不让生成模型一句自评“合格”就自动入库。审核模型只是辅助，不是准确性的保证。
4. **先小批人工复核。** 可先挑 30–50 张典型卡作为试点，对新增问句全量检查；确认规则后再考虑普通卡抽检。保修/费用/安全相关问题建议逐条复核。不通过的候选不进入正式索引，保留原因以改进生成约束。
5. **单独验证检索收益。** 固定代码、原卡、embedding 与 reranker 配置，对比扩充前后目标卡 Top-1/Top-3 命中、错机型/错症状召回和无答案问题表现，再跑端到端回归。报告实际样本数及新增/解决的 Bad Case，不只报告拦截率。原有 300 条独立验证集不用于生成、筛选或阈值调优；一旦据其逐例改动，应将其转为回归集，并另取新留出数据作最终验证。

**审核提示词草案（待实现）：**

> 只依据给定知识卡，判断它能否回答候选问句。逐项核对产品范围、故障现象、否定条件、用户诉求和答案适用前提。问法不要求字面相同，但不得增加根因或扩大适用范围。输出 decision（accept/reject/review）、reason、supporting_evidence（卡片原文片段）。卡片信息不足时返回 review，不补造依据。

**示例（非真实项目案例）：** 原卡针对“显示正常、触摸无响应”；“画面有，手点屏幕没反应”可列为待审核候选；“屏幕黑了开不了机”应拒绝；“大屏坏了怎么办”过于宽泛，不宜直接作为该窄场景卡的等价问法。是否最终接收需对照原卡全文，而非只看标题。

后续讲述应区分：“已使用真实问法辅助扩充相似问”是本人确认的工作；“规则 + 语义审核 + 人工复核 + 独立回归”是本轮建议，不在实施验证前写成过去完成的成果。

#### 4.4 RAG 算法详解与面试要点

本节依据 2026-10-13 本地代码核实。参数是代码默认值，不代表当前部署的实际配置；模型、阈值和权重需要结合对应评测 run 的配置解释。以下描述系统算法，不自动将全部实现归于个人。

**A. 先区分两条链路**

- 泛文档 `/search`、`/answer`：文档切片、章节导航及 BM25 等能力；适合讲通用文档问答背景。
- 客服知识卡 `/api/v1/knowledge-search`：本项目核心，四字段的向量与 pg_trgm 召回、RRF、可选重排、门控；**不要把这条链路里的 pg_trgm 说成 BM25，也不要把 PageIndex 当成本接口必经步骤**。

**B. 候选过滤与知识表示**

先按 project、product_scope、可选 intent/knowledge_type 和 already_tried 筛卡，再对候选做检索。过滤过严会在召回前丢掉正确卡。代码支持 thorough 模式在产品过滤无结果时放宽 product_scope，但放宽意味着适用机型需要进一步确认，不宜理解为任意跨产品套用方案。

知识卡的标题、故障描述、解决方案分别有向量字段；相似问在子表中逐条向量化。查询只生成一次向量，在各字段上检索；这要求查询与知识卡向量使用兼容的模型和维度。迁移 SQL 中有 1024 维版本，但当前 `app/settings.py` 的 `embedding_dim` 默认值为 768，部署还可注入模型，故不能凭旧笔记断言当前一定是 BGE-M3/1024 维。

**C. 八路召回**

四个字段为 title、similar_question、fault_diagnosis、solution；每个字段两路：

- 向量路：SQL 按 pgvector `<=>` 距离升序，返回 `1 - cosine_distance` 作为原始相似度，服务层融合时使用名次而非原始分数。
- 字面路：SQL 使用 pg_trgm 的 `similarity(text, query)` 并按阈值过滤。该分数不是词项 BM25 分数，也不是精确匹配；真实型号约束仍应由产品过滤等机制承担。

实现用 `asyncio.gather` 并发发起八路召回；代码默认每路 20 条、trigram 下限 0.15，因此默认最多先收集 160 条命中记录，再聚合到卡片，最终独立卡片数通常更少。查询是否实际走近似索引需执行计划验证，不能只因为使用 pgvector 就声称每次都走 HNSW。

**D. RRF 与字段权重：精确到当前实现**

排名从 1 开始，单路名次贡献为：

`contribution = 1 / (k + rank)`，默认 `k = 60`。

普通字段每张卡一条记录；同一卡的多个相似问则可在同一路占多个名次。当前最终召回分数为：

`score(card) = Σ字段 weight(field) × Σ该字段两路 Σ属于该卡的命中记录 1/(60 + rank)`。

默认字段权重：标题 3.0，相似问 3.0，故障描述 1.5，解决方案 0.7。选择这些字段权重的具体实验依据仍需补充，不能把默认值说成已验证的全局最优。RRF 避免直接混加不同检索器的原始分数，但也舍弃了原始分数差距的信息；k、权重与候选数均应在开发集调节。

**与本人相似问扩充直接相关的风险：** `_rrf_scores_question` 是**累加**同一卡多条问句的排名贡献，不是只取最好一条。因此某张卡扩充得多，可能仅因命中问句多而抬高分数、占用候选名额。repository 的注释写着最大值聚合，与服务层实际代码不同，以实现为准。优化可比较每卡每路 max 聚合、限制贡献条数、近重复去重等策略，但需保留有用问法多样性并做对照，不把它们当成已修复成果。

**E. 重排：对 query-card 联合评分**

默认 rerank 开关为 False；开启且服务可用时，先取 RRF 排名前 30 张候选卡，拼接标题、最多前三条相似问、故障描述及解决方案，发送 TEI `/rerank`，配置中的 reranker 默认名称为 `bge-reranker-v2-m3`。请求包含 `raw_scores=false`，按返回分数重新排序，再截取 top_k；该 API 不在每个请求内发送模型名，因此实际服务模型仍需核实。

这一步是**用重排分数替换最终排序分数**，不是和 RRF 分数再次加权。重排只能处理候选池内的卡，不能找回已被预过滤或召回截断丢失的卡。服务失败回退到 RRF；截断输入和只取前三条相似问的策略可能丢信息，扩大输入/候选池也会增加调用成本，需测时延而非只看命中率。

**F. 门控与归因**

默认 `knowledge_min_confidence=0.30`，请求阈值优先于服务设置；Top-1 达阈值才返回 best，否则 best 为空，但 hits 仍可返回。Agent 当前已核实的客户端取 best，不等于一定会读取 hits 自行兜底。

重要局限：重排开启时 score 是模型返回的相关性分数，关闭/失败时 score 是加权 RRF 分数，两者量纲不同，而当前共用阈值。回退排序不代表回退后的门控效果仍一致。建议按评分模式分别校准阈值，明确记录 score_type；不能把 0.30 解释为“30% 回答正确概率”。

`field_contributions`、`channel_contributions` 和 matched_by 来自召回融合分数，供诊断哪路提供候选使用；**不解释 reranker 为何改变排序，也不是模型的因果解释**。标题归因有默认 5% 的接近时优先规则。

**G. 算法如何评测，而不是只报拦截率**

准备 query 与人工确认的相关卡集合，按产品线、短句/多轮指代、含型号、无答案等切片，固定数据与配置：

- 召回：若每题一个目标卡，用 Hit@k（目标卡进入前 k 的查询占比）；若有多个相关卡，可用 Recall@k（相关卡被检出的比例，说明宏平均口径）。
- 排序：MRR 衡量首张相关卡的位置；另看 Top-1 是否正确。
- 门控：同时看接受结果中的正确比例、有答案被拒绝、无答案被放行，避免只提高阈值导致“看起来很准但什么也不答”。
- 工程：分阶段延迟、P95、embedding/rerank 失败率、降级比例。性能数字只填实测值。
- 对照：向量单路 → 向量+字面 → 字段权重 → rerank；相似问扩充、每卡聚合策略与 Query 改写分别对照，不将同时改变多个模块的总收益归因于单一算法。
- 1000 条参与迭代的会话可用于开发回归；300 条未参与调优的会话用于独立端到端验证。若要评测卡片检索，需另确认其中 query-card 相关性标注，不能把未转人工率直接当检索准确率。

#### 5.3 少锡的实际排查步骤

4. **转入工艺检查子树。** 大面积、共性、偶发和关键数据缺失各挂一套检查子树，按配置优先级检查 PCB 焊盘异物、翘曲、绿油、刮刀、钢网形变、堵孔、人员操作、顶针、印刷参数、印刷机及 SPI 设备等。截图中的“PCB来料不可移动异物”对应 `检测PCB焊盘异物=是` 的叶子分支，不是模型自由生成的结论。
5. **继续细分或收敛。** 例如堵孔进一步检查印刷机内异物、锡膏结块；结块相关分支会读取回温、开封/未开封放置时间和有效期，也包含人工检测项。框架将完成的叶子收集为诊断原因并回溯激活路径。

主要入口：业务 `diagnosis/shaoxi/udf_new.py:detect_stencil_commonality` → `_build_fixture_commonality`；分组规则在 `diagnosis/_viz/group_defects.py`。

1. **构建参考样本。** `_commonality_sample` 从检测结果表取同产品、同 SPI 设备、同报警类型、事件时刻之前（含当前时刻）近 5 日的已报警板，按 SN 聚合、剔除光板，再按时间取最多 100 块。当前实现**包含当前板**；调用处还有“排除当前板”的陈旧注释，以实际 SQL 为准。
2. **绑定生产工装。** `_collect_fixture_groups` 根据产线及每块板的报警时刻，取之前最近一次钢网上机记录，形成“一板一网”的关联；使用的是 `usage_count`，虽下游字段仍沿用旧名 `total_usage_count`。这是时序关联 SQL，不是知识图谱自动推断。
3. **统计集中性。** 按网号统计去重不良板数。当前 `VERDICT_RULE='ratio'`：最高组数量至少为其余非并列最高组平均的 **1.8 倍**，且至少 **3 块**；并列最高组一起处理。文件还保留均值＋一倍总体标准差的可选旧方案，不能只照模块注释说当前一定用 sigma。
4. **输出证据。** 展示分组不良板数、当前板对应钢网、使用次数及使用次数区间分布。使用次数集中性图是附加证据，**不参与该节点最终判定**；任一工装达到判据即可触发共性，不要求它恰好是当前板所用钢网。
5. **驱动流程。** 返回“异常/正常”供共性总节点汇总，形成共性分支并继续工艺检查；不直接得出“这张钢网造成缺陷”的最终根因。

需理解的两个限制：这是已报警板的**数量集中性**，没有各钢网正常生产总量作分母，不能称为缺陷发生率或因果效应；用报警时间近似印刷时间也可能在换网边界造成关联偏差。单一分组或各组一样多时图文显示不可判定，但节点返回仍可能为正常，属于重构的状态语义切入点。

#### 5.5 其他自动分析与人工接续

- **CPK：** `detect_cpk` 匹配异常检测项的 SPC 维度，查询指标服务预计算的当日 CPK，已有值最小值 ≥1.33 时返回正常，否则异常；完全没有值则不可用。配套生成 SPC 控制图证据，不是在每个工单现场重算所有 CPK。
- **3σ：** 查询当前测量值及近 7 日历史，每个检测项最多 125 条参考，使用 `ThreeSigmaModel` 做分布排查。其采样与钢网“近 5 日最多 100 块已报警板”不是同一口径，不能混写。
- **人工输入：** `core/_owl/models/graph_nodes.py` 读取检测标准：枚举项生成单选卡；数值项优先查后端，无值再要求人工填写，并按上下限/规则归一化。角色绑定、附件要求和重新指派入口用于现场协作。
- **暂停恢复：** 交互需求转为 waiting/todo，BPMN 外层暂停。反馈带执行标识回传后恢复 OWL 状态和上下文继续执行；不是重新跑一整场自由对话。
- **持久化：** `core/_bpmn/state_manager.py` 将上下文、节点历史、OWL 运行状态和 todo 写入 PostgreSQL 的 `agent_session_record`，按 session UPSERT。代码提供重跑/局部恢复；不能仅凭“checkpoint”名称宣称已有每次保存的独立历史版本库。
- **标识与缓存：** 条件 `node_id` 按源节点隔离，`cache_key` 用于共享同名检查取数，`execution_id` 关联具体待办。需要同时避免卡片覆盖和重复查询，是该实现的重要工程细节。

#### 7.3 模型具体提取什么

`build_ontology_prompt.py` 整理文档与 schema，**由外层主 Agent 的 LLM 提取**，CLI 内不再启动第二个建树 LLM。输出是包含 creates/updates/deletes 的 `apply-plan` JSON，不是自由文本总结。

| 对象 | 含义 | 建模边界 |
|---|---|---|
| FailureSymptom | 顶层现象、中间异常、根因节点 | 表达“什么异常”，不把“检查一下”当成故障 |
| OntologyTest | 检查项、输入类型、选项、阈值及提示 | 表达“检查什么、怎么判断” |
| SymptomTransition | 上下游节点、绑定检查项与路由条件 | 表达诊断分解关系，不是报告叙述的先后顺序 |
| OntologyMeasure | 处置或改善措施，并挂接适用症状 | 不为凑齐字段补造措施和成因 |

- 本体层级是 `start → inner → root`；其中 root 表示终止根因。导出后映射为执行图 `ROOT → INTERMEDIATE → LEAF`，注意两套命名中的 root 含义不同。
- 字段状态区分原文明确提取、依据资料推断、缺失等；`chunk_ids` 关联文档片段。它们用于保留来源与不确定性，不是经过校准的置信概率，也不代表代码已经验证每项结论被原文蕴含。
- 技能要求先查询现有实体，按需搜索并复用检查项，避免盲目新增。搜索器当前默认字符级 BM25；BGE-M3 向量相似度重排是关闭的可选分支，不能写成默认启用 Cross-Encoder 或全自动语义去重。
- 示例（仅解释建模，不作为实际导入案例）：报告记载“少锡，检查发现钢网孔堵塞，清理后恢复”，可对应现象/原因、钢网孔检查、检查结果触发的边和清理措施；不应自行补出报告未记载的堵塞成因。

#### 7.4 为什么不是“提示词一次生成一张图”

1. **分支级增量构建。** 技能要求按完整分支分批生成计划，每批约不超过 15 KB，查询并复用既有 ID，减少大输出超时和重复节点；这是技能执行约定，不是 CLI 强制的大小限制。
2. **确定性变更工具。** `ontology_cli.py:_run_apply_plan` 复制原 TTL 到临时目录，在副本创建实体/关系及更新删除，统一校验后才复制回正式文件。校验失败不覆盖旧文件，已成功批次可保留；实现用 `shutil.copy2`，不是数据库事务或崩溃安全的原子文件替换。
3. **结构门禁。** SHACL 约束配合 Python 图遍历检查环路、同一入口下多父汇聚、连续中间层深度、树入口唯一性、中间节点能否到达根因、节点能否回溯到顶层等。Violation 阻断，Warning 保留提示但允许通过。
4. **校验反馈用于修正。** 工具返回结构化成功/失败及错误说明，技能要求修复后重试；图结构合法不等于诊断知识正确，业务语义仍需要专家审阅和案例验证。

#### 7.7 面试讲述主线（文字稿）

> 这个项目分为知识构建和诊断执行两层。知识构建阶段，我们利用大模型从 8D、历史工单和 FMEA 等工艺资料中提取失效现象、原因关系、检查项与处置措施，形成结构化故障树草稿。模型输出不是直接上线，而是经过图结构与字段校验，再转换成诊断系统使用的配置。在线阶段由执行器结合产线数据分析工具和工程师检查反馈推进排查，记录证据并形成诊断结果。这样既降低专家经验结构化的成本，又避免在线诊断完全依赖大模型自由判断。

### 4. 算法主线与可讲清的细节

**输入是什么？** 每条曲线是按时间顺序排列的 `L × 2` 矩阵，两列是压力和位移；时间戳用于组织序列，不是文档规定的第三个模型特征。这里的“二维”指两个特征通道，不是把曲线转成图片送入视觉模型。

**模型学什么？** 编码器把正常曲线编码为低维隐状态，解码器据此重构输入。训练目标是降低输入与输出之间的重构误差，文档举例使用均方误差。异常判定的依据是重构误差超过预设阈值，而不是 LSTM 直接输出某个故障类别。

**用公式解释（按文档所举、所有点等权的 MSE 示例，不代表已核实代码）：**

`score(X) = sum((X[t, feature] - X_hat[t, feature])²) / (2 × L)`

`score(X) > threshold → 标记为异常候选`

该解释建立在使用两个通道、所有 L 个点共同计算误差的前提下；代码是否采用 mask、通道权重或不同误差聚合方式尚未给出。不能自行补上模型层数、隐藏维度、优化器、训练轮数、阈值分位数等参数。

**技术优势应怎样讲？** 方案以正常样本学习序列模式，提供了超出少数极值/拐点特征的建模方式；工程上把采集、训练、边缘推理和预警串联起来。重构误差作为异常信号的有效性仍需用具体样本验证，不能承诺所有异常都会高误差，也不能把正常样本训练称为模型能够自动适应所有新工况。

### 5. 面试中最值得展开的三个设计取舍

本节是依据交底书整理的讨论点，不是额外声称已经实现的优化。

1. **为什么只用正常样本训练？** 文档明确采用正常样本训练，可以据此解释正常模式学习。是否因为实际异常样本稀缺、是否有独立异常验证集，要看后续数据材料，不预写异常样本数量或比例。还需区分“偏离正常曲线”和“经现场确认的真实质量缺陷”。
2. **为什么用长度 95% 分位数，而不是最长序列？** 文档给出了规则，但未给出选参实验。可以讨论统一输入尺寸和长序列信息保留之间的取舍：保留前 L 点可能截掉末端信息，填充点也可能影响误差；需要结合异常所处阶段、有效长度及实际损失实现分析，不能声称已验证为最优或无损。
3. **为什么把模型和预处理配置一起交付？** 文档明确记录 L 与填充策略，核心是保持训练/推理输入一致。压力与位移单位不同，是否做特征缩放及如何保存缩放参数是代码核查重点；不能把“长度标准化”混同于 z-score 或 Min-Max 归一化。

此外，文档提到推送“异常类型”，但正文模型只定义了重构误差判异，尚未给出类型识别逻辑；现阶段宜讲异常告警与曲线回看，不讲已能自动根因诊断。“实时”也先解释为采集到曲线后的边缘端判定，不自行扩展成压装进行中的逐点控制、自动停机或闭环调参。

- **规则和数据驱动方案如何配合？** 哪些明确失效现象由规则识别，哪些未知形态由模板距离和离群检测筛出；二者是独立可选模式还是融合输出，以实现为准。
- **何种差异可以对齐，何种差异必须保留？** 检查 DTW 是否把真正有质量意义的阶段长度或角度差异对齐掉；角度和包络检验在实际逻辑中承担什么角色。
- **标准曲线如何避免被异常污染？** 近 14 日数据不自动等于正常数据，需看选样、产品切换及基线更新规则；不能只因基线跟随变化就认定工艺变健康。
- **如何区分过程异常与真实不良？** 看复判证据、检出率和误报量，而非仅以模型与原工具 OK/NG 一致率评价效果。
- **多判据怎样作最终决策？** 记录触发窗口、DTW 匹配、包络偏离和角度检查等证据；不凭“多维交叉确认”四字补造 AND/OR、投票或加权融合公式。

#### 11.7 多策略独立判异与分级处置

**方案选择：** 2026-10-15，用户认可将该设计纳入项目底稿。三种方法各自检查曲线，再由决策层按风险类型汇总，不以任意一路“正常”作为跳过其他检查的条件，也不采用简单三选二投票。

**处理流程：** 数据有效性检查 → 各路独立判异 → 汇总证据与运行状态 → 风险分级 → 现场复核及既有生产流程处置。

- **判异框：** 基于关键点和 3σ 标定结果检查关键工艺区间，保留命中区间及越界情况。
- **孤立森林：** 对五个阶段提取的统计特征进行异常检测，保留异常分数及输入特征供回看；不声称模型分数本身已经定位物理根因。
- **LSTM 自编码器：** 对完整输入序列重构，保留重构误差及对应曲线，提供整体形态层面的风险依据。
- **工艺硬约束（如现场另有明确要求）：** 与统计判异框分开配置和记录，只有经工艺确认的强制限制才按硬约束处理，不将所有 3σ 越界当作明确工艺违规。

| 情况 | 汇总结果与处置原则 |
|---|---|
| 数据无效、必要模型超时或执行失败 | 标记数据/执行异常，报告未完成的检查；保留其他已发现的风险，不把缺失结果补成“正常”。 |
| 违反经确认的工艺硬约束 | 保留明确越界告警，不由其他模型的正常结果抵消；按现场授权流程处置。 |
| 单路统计或模型判异报异常 | 保留该路风险、曲线和触发依据，进入复核，不因其余两路正常而抹去。 |
| 多路同时报异常 | 标记为多路命中，提高复核优先级；这不是已确认缺陷或经过校准的缺陷概率。 |
| 所有必要检查完成且均未报异常 | 记录“本轮未检出异常”，沿用既有生产放行流程，不取代其他质量检验。 |

**为什么这样组织：** 三类方法关注不同粒度，保留单路异常提示有助于利用其互补性；代价是可能增加告警及复核量。因此把预警与控线分开，先在影子模式观察，再结合人工确认和现场要求决定处置。多路结果可能相关，不把重复命中机械解释为独立证据累积。

**执行方式：** “独立判异”指各路都保有检查机会和输出，不强制使用多线程或同时推理。边缘设备可按资源条件依次计算；即使先算的一路通过，也不因此省略后续必要检查。

**验证安排：** 在相同曲线集、标签口径和版本配置下，对照单路方法、简单多数投票及分级汇总方案，记录漏检、误报、复核量和处理耗时；既有准确率保留原所属版本，不预先归因为新增汇总设计带来的收益。

**技术方案压缩表述：**

> 结合 3σ 判异框、分段特征孤立森林与 LSTM 自编码器，设计多策略独立判异与风险分级汇总机制，保留单路异常证据，区分明确工艺越界、统计异常及执行异常，将风险预警与控线处置解耦，支持影子验证和现场复核。

**面试解释：**

> 这套方案不是让三个模型投票。判异框、分段特征模型和序列模型关注的异常不同，所以我们在设计上保留每一路发现的风险：单路异常交给现场复核，多路命中提高优先级，明确工艺越界不被模型正常结果抵消。推理失败也不会算作正常。预警和控线分开，先通过影子验证观察漏检、误报和复核成本，再确定处置策略。

**机理解释（可能性）：** 压入件与孔未对正时，先接触孔口侧边，阻力升高；随后滑入孔内，力回落，之后随压装继续而上升。该解释用于提出复核方向，不能只凭曲线唯一判定未对正或工装磨损。

**与现有项目图的关系：** 第 11.2 节的特征工程截图中，标为 OK 的示例也存在预压装峰及回落。因此“初段有峰谷”不能单独作为 NG 条件；应比较同工位、同工艺下正常样本的峰值、发生位移、峰谷差及阶段长度，判断是否偏离正常范围。

**多策略分析思路（用于面试解释，不预写实验命中结果）：**

- 判异框检查该峰及回落是否超出对应阶段的标定区间，不只检查最终值。
- 分段特征模型利用已有峰、谷、斜率、区间长度、面积及标准差描述初段；峰谷差可作为候选派生特征，是否已实现需看代码。
- LSTM 自编码器检查该形态相对所学习正常模式的重构误差；是否能检出及误差如何聚合以实际回放为准，不声称必然触发或天然定位根因。
- 现场复核关注零件对正、定位工装及磨损状况，并结合实际装配质量判断；曲线异常提示不直接替代质量结论。

**面试叙述草稿：**

> 一个容易讲清的形态是初段力先升高、回落，再继续上升。它可能对应压入件先碰到孔口侧边、随后滑入，但不能看到峰谷就判异常，因为正常预压装也可能有类似形态。我们设计判异时需要看它相对本工位正常曲线是否异常，例如峰值大小、位置和回落幅度，再结合规则、分段特征和序列模型给出的依据，交现场核查对正和工装情况。
